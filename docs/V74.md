# v74 firmware — what actually changes (verified on real v74.00.324A hardware, 2026-11)

**Bottom line: this toolkit is built and tested on v59.00.502. On v74 the
commands, paths, firewall and access model are different.** If you updated to
v74, read this before assuming the v59 docs apply. Where a v74 path exists in
the toolkit it is named explicitly (e.g. `net/autostart-v74.sh`,
`ssh/sshd_config_v74`); `autorun` auto-detects v74 via `/jci/version.ini` and
runs the v74 bring-up.

## 1. Access after a v74 update — everything v59 gave you is gone

A v74 `.up` update overwrites the eMMC rootfs. Consequences, all verified live:

| v59 behavior | v74 behavior |
|---|---|
| sshd on port 36000 reads our key from `/data_persist` | stock v74 sshd reads **`AuthorizedKeysFile /config-mfg/authorized_keys`** — a read-only NOR partition that contains **only the Mazda key**. Your key is rejected. You need your own sshd (`ssh/sshd_config_v74`) with keys in `/data_persist` |
| `/data_persist/dev/bin/autorun` hook | **`neutralizeid7` deletes it during every update** — after each `.up` you must re-install the rescue/autorun hook |
| USB autorun / rescue stick | **jci-autorun is compiled OFF on v74**: `UPDATEA_SYS_SRV_enableUsbDbgScript` is a const `0` in `svcjciupdatea.so` (disassembly-proven) — the "Start execute USB Debug Script" string exists but the flag check is always false. USB sticks are mounted but never executed |
| Serial console `user`/`jci` | shell is `/bin/shsshd` (broken) → no shell. **But `cmu` serial login works on v74 and is uid 0 (root)** — serial is a working root route on v74 |
| stage scripts `stage_wifi.sh` etc. with content | **empty (shebang only)** — but `sm` still executes them, so a hook line still works. `start_network.sh` has real content and runs as root (loads usbnet/asix, starts eth1 DHCP, starts sshd) — good hook point |

## 2. Firewall — ping is dead, SSH is not

v74 `jci-fw.sh` sets `-P INPUT DROP` and **drops ICMP echo-request** (rule
~130), while **TCP 36000 is ACCEPTed** (rule ~115, but not on wlan0).
Symptom: `ping <CMU>` fails from your laptop, but SSH works. Fix:
`iptables -I INPUT -p icmp --icmp-type echo-request -j ACCEPT`
(toolkit: `net/autostart-v74.sh`).

## 3. WiFi

Same wl12xx driver, but v74 ships newer chip firmware (`sr.bin` FRev
7.3.10.0.142 vs v59 .136). On our board that produced **more** watchdog
crashes, not fewer — see WIFI.md root cause. Rollback path:
`wifi/rollback-firmware-v59.sh`. NMS D-Bus connect differs on v74 — use
`wifi/connect-v74.sh` / `wifi/scan-v74.sh` (different D-Bus service names and
methods; the v59 `connect-nms.sh` calls will return UnknownMethod).

## 4. Terminal from the GUI — different event chain

On **stock v74**, `ReadDTC testId=22` is **dropped**: `startSystemScripts.sh`
only knows code **11**. The terminal is diag menu **item 10 (page 2, after
"Next")**, normally reached via `systemHooks.sh 22` triggered by a *native*
mouse click in `jci-systemDialog` (a native Wayland surface — synthetic DOM
clicks from Opera JS do not reach it; it has no keyboard input).

Verified working routes on v74:

- **Serial `cmu` login** (uid 0) → `sh /jci/scripts/systemHooks.sh 22`
- **SSH :36000** (with your own sshd) → same command
- GUI-only: `ReadDTC testId=11` → dialog → manually tap Next → TERMINAL
  (clunky; ghost-touch makes the synthetic tap unreliable)
- **Patch** `/jci/scripts/startSystemScripts.sh` to delegate any code ≠ 11 to
  `systemHooks.sh "$1"` → then `ReadDTC testId=22` works directly from GUI JS
  (the v59 behavior). See `docs/GUI-HACKING.md`.

Synthetic input is possible via the JCI D-Bus devices API
(`com.jci.cpp.devices.Keyboard/Mouse`: `keyClick`/`buttonClick`/`move` through
`/dev/uinput`, `libjcidevices.so` has `filtered-%s`), and `usb_drivers.sh`
loads `usbhid` — a USB keyboard/mouse works as Wayland input on v74.

## 5. Menu/UI switching on v74

The menu itself is unchanged (numeric-only, no Shift key on the terminal).
Menu → System & security → **4** still tries `ReadDTC 22` + `run-terminal.sh` +
`systemHooks.sh 22` fallbacks; on stock v74 only the `systemHooks.sh 22` path
fires when you have shell access. Option **5** (close terminal, back to UI:
`killall terminal` + `ivi-shell -f "Main"`) works the same on v74.

## 6. Recovery on v74

If v74 boots into a loop, the v59 software routes are dead (see
RECOVERY-BRICK.md) **and** USB autorun is compiled out — the remaining routes
are serial `cmu` login or the CH341A SPI-NOR boot-select flip.
