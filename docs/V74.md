# v74 firmware — regaining and keeping root (verified on real v74.00.324A hardware)

**This toolkit is built and tested on v59.00.502. v74 is a different access
model** — after a v74 update your SSH key, boot hooks and firewall are reset,
USB autorun is compiled out, and ping is firewalled. This page is the working
recipe to get back in on v74 and make it survive reboots.

Verified on **v74.00.324A EU N** (`JCI_SW_VER MAZ_CMU-150_74.00.324`, kernel
3.0.35 armv7l, OpenSSH 5.9p1).

- Toolkit: the v74 variant lives in [`toolkit-v74/`](../toolkit-v74/) (the v59
  base plus the v74 pieces: `lib/ensure-rw.sh`, `ssh/sshd_config_v74`,
  `net/sshd-up-v74.sh`). **The v74 variant is untested except for the SSH
  bring-up** — see [`toolkit-v74/README-V74.txt`](../toolkit-v74/README-V74.txt).
- Script: [`toolkit-v74/net/sshd-up-v74.sh`](../toolkit-v74/net/sshd-up-v74.sh) — the
  one-shot bring-up (own sshd on 2222, firewall, routing), runs entirely from
  `/tmp` + `/data_persist`, no rootfs write. **This is the one part proven on v74.**
- GUI terminal event chain on v74: [V74-GUI-TERMINAL.md](V74-GUI-TERMINAL.md)
- Background (rootfs diff, safe update procedure): [research/](research/)

## TL;DR — the working route

1. Get a root shell on the CMU: **serial `cmu` login** (uid 0) or the **diag
   menu terminal** (`ReadDTC testId=11` → dialog → tap Next → TERMINAL).
2. Get `sshd-up-v74.sh` onto the car (USB stick / paste) with your RSA pubkey
   set (see the script header), and run it as root:
   ```sh
   sh sshd-up-v74.sh
   ```
3. From your laptop (direct USB-ethernet cable, laptop = `192.168.0.1/24`):
   ```sh
   ssh -i /path/to/id_rsa -o IdentitiesOnly=yes \
     -o PubkeyAcceptedAlgorithms=+ssh-rsa -o HostKeyAlgorithms=+ssh-rsa,ssh-dss \
     -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null \
     -p 2222 cmu@192.168.0.2
   ```
   → `uid=0(cmu)`, Linux 3.0.35 armv7l.
4. To survive reboots, hook the script into `/jci/scripts/start_network.sh`
   (section 4). To survive the next `.up` update, re-deploy it (section 3).

Why 2222 and not the stock 36000: the stock v74 sshd reads
`AuthorizedKeysFile /config-mfg/authorized_keys` — a read-only NOR partition
with **only the Mazda key**. Your key is rejected. So you run your **own** sshd
on **2222** (avoids a respawn conflict with the stock one) with keys in
`/data_persist`.

## 1. What a v74 update destroys — and what survives

A v74 `.up` update **overwrites the eMMC rootfs** (`/`, a relfs on
`/dev/ffx01p1`). All verified live:

| Item | Fate on a v74 update |
|---|---|
| Patched `/etc/ssh/sshd_config` and any rootfs boot hook | **Gone** — rootfs is replaced |
| `/data_persist` (your stored keys) | **Survives** (`cleandatapersist` only trims `log/dumps` > 150 MB) — but nothing points to it anymore |
| `/config-mfg` (NOR squashfs, `/dev/mtdblock5`) | **Survives**, but update step `passwdupdate` remounts it rw and commits **Mazda's own** `authorized_keys` + a fresh `passwd` |
| `/data_persist/dev/bin/autorun` hook | **Deleted by `neutralizeid7` on every update** (plus `00-*`, `01-*`, `99-*.autorun`, `adb`) |
| USB autorun / rescue stick | **Compiled out** (section 5) — sticks are mounted but never executed |

So after each `.up`: your key file may still be in `/data_persist`, but you
must re-deploy the bring-up (sshd + hook).

## 2. Why direct SSH fails on a fresh v74

Stock v74 `sshd_config` (byte-identical to v59):

```
Port 36000
AuthorizedKeysFile /config-mfg/authorized_keys
PasswordAuthentication no
PermitRootLogin yes
```

`/config-mfg/authorized_keys` holds **only the Mazda key**, so your key is
rejected on 36000. The fix is your **own sshd** on **2222** pointing at your
own `authorized_keys` — exactly what `sshd-up-v74.sh` sets up. Key notes:

- v74 runs **OpenSSH 5.9 — no ed25519.** An **RSA** key is mandatory; connect
  with `-o PubkeyAcceptedAlgorithms=+ssh-rsa -o HostKeyAlgorithms=+ssh-rsa,ssh-dss`.
- Rootfs is read-only; to write it you need `mount -o remount,rw,sync /` — the
  **`sync` is required**, plain `remount,rw` fails on v74. The bring-up script
  avoids this entirely (it runs from `/tmp`).
- `/etc/passwd` is a symlink to the read-only `/config-mfg/passwd` (`$5$` hash),
  so `chpasswd` fails. The script replaces it with a real file carrying a DES
  hash so `cmu`/`mzd` serial login works (section 6).

## 3. Firewall — ping is dead, SSH is not

`start_network.sh` runs `jci-fw.sh start WCP`, which on v74 does:

```
$IPTABLES -P INPUT DROP
$IPTABLES -A INPUT -p icmp --icmp-type echo-request -j DROP           # ping dies
$IPTABLES -A INPUT -p tcp --dport 36000 -m state --state NEW,ESTABLISHED -j ACCEPT
```

Symptom: `ping <CMU_IP>` fails from your laptop while SSH works — that is
expected, not a link problem. The bring-up script opens the link and your port:

```
iptables -I INPUT 1 -i eth1 -j ACCEPT
iptables -I INPUT 1 -p tcp --dport 2222 -j ACCEPT
```

If ARP works but you still get `connect timed out`, it is reverse-path
filtering — the script sets `rp_filter = 0` and adds an explicit host route
back to the laptop.

## 4. Persistence across reboots: the start_network.sh hook

The rootfs relfs is **not** wiped on reboot (only on a firmware update), so a
hook in the rootfs survives reboots. The reliable hook point is
**`/jci/scripts/start_network.sh`** (real content, runs as root at boot).
Append one line, keep a backup, and `sh -n` both files:

```sh
cp /jci/scripts/start_network.sh /jci/scripts/start_network.sh.mzdbak
printf '%s\n' '[ -x /data_persist/dev/sshd-up-v74.sh ] && /data_persist/dev/sshd-up-v74.sh > /data_persist/dev/sshd-up.boot.log 2>&1 &' >> /jci/scripts/start_network.sh
```

(Copy `sshd-up-v74.sh` to `/data_persist/dev/` first; `mount -o remount,rw,sync /`
before editing the rootfs file.) This survives reboots but **not** the next
`.up` — after an update, re-run section 1–2 and re-add the hook.

## 5. jci-autorun USB hook is compiled out on v74

The `jci-autorun` USB hook **exists** in the v74 binary
`jci/reflash/svcjciupdatea.so` but is **hard-disabled**:

- Flag `UPDATEA_SYS_SRV_enableUsbDbgScript` lives in `.rodata` at **`0x43958`**,
  value **`0`** — a read-only const with no relocation (GOT entry `0x5953c`,
  `R_ARM_RELATIVE` addend `0x43958`).
- Both call sites check `*flag == 1` before calling `SearchAndExecUSBDbgScript`:
  - `updatea_sys_usb_AttachedDevEvent` @ **`0x2c02c`**
  - `updatea_sys_usb_GetStorageDevicesListFromUSBMGR` @ **`0x2cef8`**
- The value is always 0, so the check is always false and the hook **never
  fires** on v74.

This is why a `jci-autorun` rescue stick "does nothing" on v74 (not timing, not
CRLF, not the USB port — the facility is off in production firmware). On v59 the
same stick works; on v74 use serial or the diag terminal instead.

## 6. Serial console: `cmu` root login works on v74

- The `user` account's shell is `/bin/shsshd` (broken) → dead end.
- **`cmu` serial login works on stock v74 and is uid 0 (root).** 115200 8N1,
  one program on the COM port at a time.
- The symlinked `/etc/passwd` has an unknown `$5$` hash, so set a known one:
  `sshd-up-v74.sh` writes a real `/etc/passwd` with a DES hash so `cmu`/`mzd`
  works over serial. Serial is a reliable root route on v74.

## 7. WiFi

Same wl12xx driver, but v74 ships newer chip firmware (`sr.bin` FRev
7.3.10.0.142 vs v59 .136). On this board that produced **more** watchdog
crashes, not fewer — see [WIFI.md](WIFI.md). Rollback:
`wifi/rollback-firmware-v59.sh`. NMS D-Bus connect differs on v74 — use
`wifi/connect-v74.sh` / `wifi/scan-v74.sh` (the v59 `connect-nms.sh` calls
return `UnknownMethod`).

## 8. Recovery on v74

If v74 boots into a loop, the v59 software routes are dead (see
[RECOVERY-BRICK.md](RECOVERY-BRICK.md)) **and** USB autorun is compiled out —
the remaining routes are **serial `cmu` login** or the **CH341A SPI-NOR
boot-select flip** ([NOR-FLASH-RECOVERY.md](NOR-FLASH-RECOVERY.md)).
